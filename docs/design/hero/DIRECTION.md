# Hero loop: direction

The README opens on one animated SVG (`docs/media/hero-{dark,light}.svg`, generated by
`scripts/render-hero.mjs`). It has one job: say the governing thought before anything moves, then
show the four steps that support it, and come back to the same frame.

## The message (fixed, from README lines 3 and 17–30)

- **Governing thought.** Keep an agent-readable `docs/` folder in sync with OneDrive, SharePoint,
  Outlook and Teams by processing only what changed.
- **Key line, in time order.** Each step exists so that the next one can skip work.
  1. Ask each source what changed, and make expiry cheap.
  2. Decide with three hashes before reading a byte.
  3. Read bytes only on purpose.
  4. Publish a pure function of the source, in git.

Frame 0 shows all of it, the governing thought and all four steps, in full contrast, over the
**outcome** of a sync: `2 of 256 read`, two amber cells in a grey field, and the funnel that got
there. The loop never hides the governing thought. That matters because a browser can hand a returning visitor a cached
image whose timeline is already running, so "legible at t = 0" is not enough: the answer has to be
legible at every t.

## The one motion idea: tempo means cost, the same way colour does

VISUAL.md makes colour mean cost. The hero makes **time** mean cost as well. Free work is instant,
small and neutral. Reading bytes is the only slow motion on screen and the only amber. Because the
design's claim is that almost nothing costs anything, **most of the loop is stillness**, and that
stillness is the argument. A viewer who watches one cycle should come away with one sentence:
*almost everything was decided without touching a byte, and the one read was the loud thing.*

## Motion vocabulary: each motion means exactly one thing

No motion is decorative, and no meaning has two motions.

| Motion | Means | Property | Timing |
|---|---|---|---|
| **ring**: a **muted** outline appears around a cell | a source reported this object. Metadata only, free. (The rings *are* the answer to the ask, so the ask itself has no motion.) It is muted because a zero-cost mark must never outrank the one paid mark | `opacity` | 200 ms, `settle` |
| **walk**: a 1.5 px muted line crosses one source's block at constant speed | a metadata listing, reading zero bytes | `transform` | 1.0 s, `walk`: faster than a read, because it reads nothing |
| **expire**: a since-token turns red and shows `410` | a token expired, by design | `opacity` | 150 ms in, **held until the walk ends**, 400 ms out |
| **exit**: a green outline replaces the ring, holds 0.7 s, then fades back into the grey field. The object has left the work, so the field goes quiet again. The one H2 exit keeps a **2 px** green frame through the outcome, so "paid, then free" (framed amber) differs from "paid and published" (bare amber) in shape, not only in hue | a free early exit: unchanged at H0, or a no-op save at H2 | `opacity` | 300 ms `settle` in, 500 ms `leave` out |
| **read**: amber rises through the cell at a constant rate and **stays** until the reset. Bytes, once paid for, never drain | bytes materialised. **The only amber motion, and the only slow one** | `transform` (scaleY) | 1.6 s, `walk` |
| **write**: a line segment draws itself and a commit dot appears | something is committed to git | `stroke-dashoffset` + `opacity` | 600 ms, `settle` |
| **travel**: a text-coloured page mark moves from a cell to above the git line, then drops onto it as the line is drawn | converted markdown going to `docs/`. It is text-coloured, not amber, because what is committed is not source bytes | `transform` | 800 ms `travel` over, then 200 ms `settle` down. It is the longest move in the scene (≈ 750 px), so it gets the most time. |
| **focus**: the other key-line steps dim | where the argument is | `opacity` | 300 ms, `travel`. The dim is **55 % in dark and 65 % in light**, and both clear 4.5:1 (measured). 55 % in light is 3.65:1 |

Animated properties are `transform`, `opacity` and `stroke-dashoffset` only. There are no animated
filters, no `foreignObject` and no script, since GitHub serves the file through `<img>`.

## Easing, named

| Name | Curve | Used for |
|---|---|---|
| `settle` | `cubic-bezier(0.16, 1, 0.3, 1)` (expo out) | arrivals: a ring, a line being written |
| `leave` | `cubic-bezier(0.7, 0, 0.84, 0)` (expo in) | exits: an object leaving the flow for free |
| `travel` | `cubic-bezier(0.65, 0, 0.35, 1)` (cubic in-out) | moving between decisions, and focus changes |
| `walk` | `linear` | anything mechanical and metered: a metadata walk, bytes streaming in |

There is no overshoot and no spring. A bounce reads as play, and this is plumbing.

## Time

- **T = 30 s.** The story is front-loaded: the first ring is at 3.5 s, the first read at 11 s, and
  the commit is on screen by 18 s, so a 15 s glance sees amber. The last 5 s, plus the first 3,
  make an 8 s still frame across the seam. (The storyboard critic proposed 25 s. 30 s keeps its
  timings and inside the brief's 30–45 s range, and buys a 5 s hold on the outcome frame.)
- One master period **T** divides every animation. Every animated element uses the same
  `animation-duration: T` with keyframe percentages, so everything is phase-locked and the loop
  is exact.
- Beats sit on a 0.5 s grid.
- **The rest frame is the outcome** (18.5 s → T → 2.0 s, 13.5 s across the seam). It is also what
  reduced motion shows and what the first 2 s of any page load show.
- **2.0 – 2.9 s: the next sync**, in one beat. The git line slides one commit left while the last
  commit settles into history (2.0–2.5), and then the outcome clears (2.5–2.9). This replaced a
  four-beat unwind at 23–25 s that briefly showed `2 of 256 read` over an empty field.
- **3.0 – 18.5 s: the story**, one key-line step at a time, rebuilding the outcome it started on.
  The seam falls inside a still frame, so it is exact by construction.
- Each element's static attributes equal its 0 % keyframe. So `prefers-reduced-motion: reduce`
  (`animation: none`) shows exactly the answer frame.

## Type and colour

- **Geist Sans and Geist Mono (SIL OFL 1.1)**, converted to outlined paths at build time, because
  GitHub's image proxy blocks web fonts inside `<img>`. One family in two roles: Sans for the
  sentences, Mono for identifiers (`docs/`, `H0`, `410`, `git`).
- Colours come from VISUAL.md's table only: text, muted, neutral, amber, green and red, each
  hand-tuned for GitHub's `#0d1117` and `#ffffff`. The background is transparent, like the diagrams.
- The dimmed key-line text must still clear 4.5:1 in both themes. That is why the dim is 55 % in dark
  and 65 % in light, and why the step numerals use the text colour, not muted.
- **One hero-only neutral:** the field's cell outline is `#afb8c1` in light, not VISUAL.md's
  `#d1d9e0`, which measures 1.43:1 on white and makes the field vanish. Dark keeps `#3d444d`.
- **Amber is drawn in the stroke tone** (`#f0a33a` / `#b35900`), never the fill tokens (1.21:1 and
  1.11:1). A read has to be the loudest thing on screen.

## What was cut

- **Typing the headline in.** The answer would be illegible at t = 0.
- **Particles, glows, gradients, shadows, blur.** None of them means a cost.
- **Microsoft product logos.** They are trademarks and noise, and the names already say it.
- **Throughput numbers.** There is no implementation yet, so any rate would be invented. The only
  counts on screen describe the scene itself.
- **Camera moves and zooms.** The viewer's eye should do the moving.
- **L6 operations, the local-versus-Graph split, and most of H1/H2's detail.** The diagrams in the
  README body carry those.
- **A blinking cursor, emoji, rotation.**

## Decisions

- **Storyboard A won** (`storyboard-verdict.md`, a fresh-context critic's scores). A is the only board
  whose picture *is* the argument: two amber cells in a still field of 256. C scored higher on the sum
  but could not show scale without growing a stage, and B erased its own answer at t = 3 s.
- **From the verdict, adopted:**
  - A stacked, answer-first layout, with the headline broken on phrase boundaries (from C).
  - A 20 px key line, and four 8 × 8 source blocks side by side, so no source is row-aligned with a step.
  - Six H0 exits, so all eight reported objects get an outcome.
  - The no-op save exits at **H2** as an `.xlsx`. README line 22 and design §4.1 both say H2 is what
    makes that save free.
  - One meter in one unit (`read N of 256`), and captions with no byte figures.
  - A clipped git conveyor.
- **Round 1 (rendered frames, `critique-round-1.md`), adopted.**
  - *The field goes quiet.* H0 exits flash green and fall back to grey, so the outcome frame is 254
    grey cells and two amber ones. Before this, green outvoted amber 7 to 2.
  - `H0`/`H2` are set in Geist Mono, because Geist Sans draws H0 as "HO". `docs/` in the headline is
    Mono too, tracked −0.04 em with a 2 px optical correction after it.
  - The stage has its own zone, 12 px lower, and the right column is on the block rhythm
    (x = 568). The meter sits on cell row 1 and the git line on the last row.
  - The two cells that will be read are dashed placeholders at rest. The amber chip covers the dashes
    as it rises, so the placeholder turns solid.
  - The meter is the stage's headline: `N of 256 read` in Mono 20, with the count turning amber.
  - A caption says `token expired: walking metadata`, with "expired" the only red word, and caption
    states crossfade with no blank beats.
  - Step 4 gives each H2 outcome its own beat: the `.xlsx` no-op save at 15.5 s, then
    `H2: 1 no-op save, 1 page updated` as the `.docx` page travels at 17 s. So no caption says "no
    commit" while a commit lands.
  - In light mode the chip is `#c86a00`, because `#b35900` fills read brown at 9 px. The meter text
    keeps `#b35900`.
- **Round 2 (`critique-round-2.md`, a new critic that never saw round 1), adopted.**
  - *The outcome is the rest frame* (see Time). Frame 0 was 256 identical cells and `0 of 256 read`,
    a riddle rather than a claim. It is now the answer with its evidence.
  - *The dashed placeholders are gone.* They marked only the two cells that would be read, which
    inverted README line 20: most of the corpus is online-only.
  - *Step 3 has a carrier:* `H0 differs on 2: budgeted reads`.
  - *A two-line ledger holds the funnel at the outcome:* `H0 equal on 6 of 8: 0 bytes read` and
    `H2 equal on 1 of 2: page unchanged`, above `+1 commit`. During the story each line first
    carries its step's event (`410: metadata walk, 0 bytes read`, then the budgeted reads), so
    "make expiry cheap" and "before reading a byte" are both stated in bytes.
  - *The committed cell's ring leaves when its page lands,* and the H2 exit keeps a 2 px frame.
  - *Rings are muted* (5.6:1 on the cell fill, where text colour was 14.8:1 and outranked the amber).
  - *The meter is Mono 24,* with its cap top on the field top.
  - *One light amber, `#c86a00`,* for both the chip and the meter. At 24 px the meter is large text,
    and 3.81:1 on white clears the 3:1 bar.
  - *The page mark leaves the bottom-row `.docx`, runs under the field and rises into the git
    line,* so it never crosses another source's objects.
- **Round 2, declined.**
  - *A narrow-screen `<picture>` variant.* The critic could not confirm that GitHub keeps width
    media queries on `<source>`, and phones are a minority of README readers.
- **A build-time guard born of round 2's seam check:** `track()` throws if a keyframe track ends
  on a value other than its rest value more than 10 ms before T. That exact mistake once re-lit a
  commit dot over 27 s and showed up only as a 180 px seam difference.
- **Deviated:** T = 30 s rather than 25 s (see Time). The travel starts from a top-row cell, so the
  page mark's path clears the `docs/` label.
- **Not changed here:** the classifier diagram labels `H1 equal` as a no-op save. That is true for
  `.pptx`, where nothing outside `docProps/` changes, and H2 catches `.xlsx` and `.docx`. The hero
  shows the H2 case and says only `H2 equal: no-op save, no commit`, which contradicts neither.

## Verification (how the frames were checked)

`scripts/hero-frames.sh` pauses every animation with `document.getAnimations()` and seeks it, then
screenshots every 0.5 s across T at 2x in both colour schemes, and builds full-frame and stage
contact sheets. It pixel-diffs t = T and t = T − 0.05 s against t = 0 (the seam) and a
`prefers-reduced-motion` frame against t = 0. It needs agent-browser, which drives Chromium only, so
WebKit and Firefox were checked separately with Playwright's builds. The same paused frames match
Chromium to within anti-aliasing (≤ 62 px beyond 15 % fuzz at 2x), and in all three engines the
loop animates inside `<img>`.
